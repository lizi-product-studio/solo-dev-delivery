# 自主交付协作

以实际交付、漏检、返工和消耗评价工作。先读原始目标、有效授权及已有结果，复用适合本领域的成熟方法；主Agent主动决定实施、检查与停止，不等用户提醒。

## 先判断本次还缺什么证据

先把用户原始痛点转成一条可实际走的因果链：触发/前置事实变化→下游动作及其业务结果→失败后合法恢复与再次读回。只看中间字段不证明下游会拒绝或恢复。对关键决策，选一组让相邻规则给出不同结果的资料；未触发决胜的样例不证明决胜规则。把明确接口的输入、返回和不变性放进少量参数化观察，不自行收紧原政策。

实现前从这条链选最危险的错误捷径；完成后问当前检查能否挡住它。等价检查合并，专业预期来自原目标，不从实现反推；普通小改用实际读回即可。
局部小改直接实施并定向读回。有状态、多条政策或多份资料也不自动建立登记表；优先复用当前产物可归属的原生测试/界面观察，只补真正缺的断言。App、小程序、网站、Agent工具与外部服务用真实界面/集成工具，缺环境保留缺口。需要独立视角时按影响使用原生委派，单纯换提示词自审不称独立。

## 本地验证的最短入口

实际加载目录为SKILL_DIR。独立包有scripts/challenge.py时S=SKILL_DIR/scripts；否则沿真实父目录找到含scripts/delivery.py和knowledge/preferences.json的ROOT，读当前偏好，S=ROOT/portable-agent-kit/scripts。不存在就说明缺失。

已有充分有效的验证不另登记。需要新本地Python场景时，控制文件放候选外，把必要结果与来源写进测试方法/注释，一次完成绑定与执行；参数例：

```sh
python3 S/challenge.py verify --workspace CANDIDATE \
  --input TASK.md --input POLICY.md --input data.json \
  --output app.py --output result.json \
  --test REVIEW/checks.py --report REVIEW/check.json
```

只声明实际依赖和交付文件，不照抄示例文件名。关键链路/决策的本地Python检查，用同一命令加`--probes REVIEW/risks.json`实际检验少量错误捷径：同一业务方法在原候选通过，在合理错误变体中必须被断言拒绝；错误变体也通过就补能区分的观察，未证明前不能停止。仅在临时副本替换声明的代码，不动真实候选、政策或数据。JSON小例见[结果核验](references/result-verification.md)的“关键观察是否真的能识别错误”；不生成全套变异或额外角色。已有充分有效的反例证据直接复用；非Python或真实界面用宿主等价反证，不伪造本地回执。

摘要显示实际缺口，完整日志留回执，失败才读细节。相同候选/脚本的证据复用，已知失败优先；修改后用新回执保留历史。测试代码受信，不是安全沙箱。
## 查到哪里、何时停止

主Agent对照原文确认：原始痛点的完整链与关键边界有实际观察，所选错误捷径被真正区分；人用关键结论从实际结果生成或直接对原依据核实，关键词存在不算一致；没有未关闭缺陷或影响交付的未知。满足即停止，不因还想得出更多场景而继续。新增检查若不能改变交付判断、与已证事实等价或超出需求，就不运行；不能把未知、跳过、一次构建、方法数量或局部PASS当充分。反例PASS也只证明所选错误可被识别，不能代替源需求和文稿核对。

失败先区分实现、需求理解、测试假设和环境原因；回到原文修复，再核原失败和共享约束的相关路径，不机械全量重跑，不新增未约定政策来迎合测试。已知业务缺陷不能通过删改断言洗绿。分批验证、覆盖争议或持久交接确需显式缺口分析时，才读[结果核验](references/result-verification.md)用既有brief/assess；它也不认证语义完整。专业判断按需读[成熟方法](references/decision-foundation.md)，软件队列细节见[本机交付](references/software-delivery.md)。

## 资源与权限

默认主Agent直接推进，按实际进展和失败证据调整方法、模型与必要委派，不堆Agent。时间、安静或预算检查点触发继续/调整/接手判断，不停止正常执行者；接手先保存成果、确认旧写入者停止。

普通任务不建持久session，已有队列继续原门禁与锁。外部结果未知先读回/对账；上线、资金、通信、费用、身份与承诺遵守本次明确授权，历史授权不迁移。定时任务保持暂停。经验只在验证有价值时更新原记录，保留来源与范围；本机新聊天读当前入口，活动聊天和其他平台的实际加载需宿主核实。
