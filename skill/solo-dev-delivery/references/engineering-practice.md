# 按风险选择工程方法

吸收 Superpowers Lite 的分流、系统调试与风险审查方法，沿用本 Skill 的目标、证据和停止判断。只读当前相关部分，不把本引用变成每轮必跑流程。

## 分流到足够的工作深度

| 当前变化 | 有价值的控制 |
| --- | --- |
| 明确、可回退、低影响的局部小改 | 实施并做定向读回或相关检查；无需额外计划文件 |
| 可观察行为改变、相关路径有回归风险 | 简述步骤，复用已有测试，检查修改差异与错误路径 |
| 架构、公开接口、跨模块依赖不确定 | 记录会影响实施的计划；有并行写入/回退需要才隔离；独立子任务明确且宿主可用时再拆分 |
| 权限、身份、不可逆数据、生产或高损失结果 | 明确边界与恢复，执行相关反证，需要时引入独立审查；外部动作核对具体授权 |

任务影响由原始目标、业务后果、不确定性、回退难度和外部副作用判断。文件数、项目名、模型名、仅仅调用Skill不决定升级；小文件也可能高风险，多文件也可能只是机械改名。需要控制时说明它解决哪个风险，已有有效计划/检查直接复用。任务扩大再判断，不机械套用TDD、worktree、全角色或审批环节。

正式队列继续使用既有 QUICK_PATCH / BOUNDED_CHANGE / GOVERNED_DELIVERY 和门禁；本表不创建新状态、不降低已进入队列任务的质量要求。语义、界面与发布仍按实际工具核验。

## 先诊断，再修复

1. 保存完整症状、输入与可复现的失败；不能复现就标明条件，先取最小有效观察。
2. 对照原始需求、最近改动、日志和可用的正常例，定位失败边界。先区分实现、需求理解、测试假设和环境。
3. 一次提出一个可被证伪的原因，用最小观察检验；没有证据不叠加补丁或无关重构。
4. 修根因，再核原失败和共享约束的相关路径。适合稳定回归的确定性问题保留测试；无法自动化时记录实际观察。
5. 多次假设失败时重查模型、依据或环境；不能靠删除有效断言、盲重试外部动作或扩大未授权范围“解决”。

环境失败不能写成业务通过。外部请求结果未知时先读回/对账，保留原请求身份，避免重复副作用。

## 审查实际变化

按影响、不确定性、变化接口、回退与副作用确定深度：低风险检查差异和相关验证；跨路径变化核需求、接口、错误处理与回归；高影响或剩余重大不确定性需要不同执行者/上下文的独立判断。串行自查可以补证，但不能声称独立。

审查从原始目标和验收判断出发：真实触发条件下，行为是否改变正确；失败/取消/恢复是否满足约定；说明是否与产物一致；是否混入无关变化。未满足要求、未关闭实质缺陷及影响交付的未知阻止完成；小问题注明即可，不为想得到的无关风险无限加测。

检查深度不等于交付结论。本系统继续使用 challenge 的当前回执、候选绑定与失败优先规则；构建、局部PASS、哈希或能力READY只证明对应范围。没有第二套 Lite DONE 报告，审查也不授予发布、通信、支付或合并权限。
